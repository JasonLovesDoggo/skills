# Pull requests

This is the authoritative guide for PR scope, evidence, and description format. Repository skills or templates supply local conventions (ticket links, required headings, workflow steps); fit them inside the shape below. Authorization to publish comes from the user's task.

## The shape

Every PR body follows this shape, top to bottom. The part above `<details>` is for a human skimming in ten seconds; the agent-written detail lives inside it.

```markdown
replace the new folder wizard's "soon" rows with crm, agent and tool rows that link to where you connect them

see prototype here: https://…

| Before | After |
| --- | --- |
| <img alt="Before: wizard with Notion and HubSpot marked SOON" src="BEFORE_URL" width="400"> | <img alt="After: wizard with CRM, agents and tools rows, each with a Connect button" src="AFTER_URL" width="400"> |

<details>
<summary>Generated by Claude</summary>

…agent-written description…

</details>
```

Keep the area above `<details>` to just these four pieces, so the reviewer sees the change itself first. The body ends with the closing `</details>` tag.

### Title

A readable English sentence describing the change the way a user or reviewer would notice it. Name the place in the product (the screen, modal, command) and what's different about it.

You can lead with a conventional-commit type when it helps: `fix:`, `feat:`, `bug:`, `security:`, or `perf:`, optionally with a scope naming the area, like `fix(folders):`. The words after the prefix still read as a plain sentence.

- `Update modal that shows after making a new folder to link to new connectors`
- `feat(search): Show a loading state while results refresh`
- `fix: Make the export command keep the original file names`
- `perf: Load the folder list twice as fast on large workspaces`

Use sentence case and plain words, and add a ticket ID only when the repo asks for one.

### One-line summary

One sentence, written the way you'd say it to a teammate: casual, lowercase is fine, everyday words. Describe what changes for the person using it. If one sentence covers it cleanly, the PR is well scoped (see **One underlying problem**).

### Prototype link (when relevant)

Add `see prototype here: <url>` when the change is UX a reviewer would otherwise experience only by pulling the branch, running a dev build, and clicking into a hard-to-reach state: flows, modals, onboarding, animations, empty and error states.

- Use the link the user gives you, or one already attached to the ticket or thread.
- When a change would clearly benefit from a prototype and there isn't one yet, ask the user whether to make one.
- Changes with nothing to click (backend, refactors, copy tweaks) go straight from the summary to the table.

### Before / After table

A two-column `Before | After` table sits directly under the summary (or the prototype line).

**UI changes:** screenshots of the same state in both columns, with matching viewport, theme, data, and zoom, cropped to the area that changed plus enough surrounding UI to orient. Use `<img … width="400">` so the pair sits side by side at a readable size, with alt text that describes what each image shows. When motion, timing, or interaction matters, add a short recording (GIF/MP4) as a second row.

- Capture "before" from the PR's base revision, or from evidence the user supplied.
- Keep PR-only media outside the repo, separate from commits.
- If you can't capture or upload media yourself, fill the cells with clearly marked placeholders (`BEFORE: <what to screenshot>`) and tell the user exactly which screenshots to drag in.

**Non-UI changes:** use the same table for the comparable evidence: CLI output, an error vs. success, a benchmark number, a lint rule failing vs. passing, a response payload. A short code block or one-line result per cell works well. For a pure refactor, the summary line can simply say "no behavior change" in place of the table.

### The `<details>` block

Label it `<summary>Generated by Claude</summary>`, with a blank line after `<summary>` so the Markdown inside renders. This is home for everything a reviewer might want to dig into:

- **What changed and why**: the underlying problem, who it affects, and the approach, in short paragraphs or parallel bullets. Point to files or implementation details where they help a reviewer know where to look.
- **Tradeoffs / limitations**: compatibility changes, follow-ups, known gaps. When one is material (a breaking change, a migration, an unverified risk), also give it a short line above the `<details>` block so it gets seen.
- **Verification**: what you ran or clicked, and what it showed (see below).
- Ticket links and repo-required sections, if any.

Size it to the change: a one-line fix might need three bullets.

## One underlying problem

Before preparing the PR, identify the underlying problem each change solves. Keep changes that solve the same problem together, including necessary supporting work, and give each independent problem its own PR. Count problems, not linked issues: several reports can describe the same defect.

A good check: the one-line summary describes one thing.

## Establish and verify the behavior

Establish the problem before changing code when possible: reproduction steps, environment, observed behavior. For a feature, establish the prior behavior and the intended outcome. If the change already exists, use the base revision or supplied evidence as the baseline and say which.

Choose checks that exercise the affected behavior: focused tests where testable, manual checks where appropriate. Match evidence to scope: a backend fix gets backend evidence, with broad test runs as a supplement to direct verification. Run repo-required checks, and repo-wide checks when required or justified by the change.

In the verification section, record exact commands or repeatable manual steps and what they showed; routine passing checks fit in one line. Name anything you couldn't check and why, and mark which results you observed versus inferred.

## Review the completed description

After drafting or updating, re-read the description against the final diff (against the PR's actual base) and any ticket, as a separate pass from reviewing the code. It's ready when:

- The title and summary line alone tell a teammate what changed, in plain English.
- The before/after table shows the change under matching conditions, or the user knows exactly which placeholders to fill.
- The prototype line appears when there's something worth clicking.
- The area above `<details>` reads like a person wrote it: summary, link, table.
- Claims inside `<details>` match the evidence and state the limits of any comparison.
- The whole PR covers one underlying problem.
- The title and body reflect the final scope of the work.

Then publish when authorized, or return the draft when that's what the user asked for.
